# Activity 1 — Signed Android release (AAB / APK)

Lab Exercise 06 · IT3060 · FitFlow mobile client (`frontend/mobile`, Flutter)

This document is the team's reference for producing, verifying and reproducing a signed FitFlow
Android release. Every number in it comes from the evidence log
[`evidence/release-evidence-1.1.0+2.txt`](evidence/release-evidence-1.1.0+2.txt), generated by
[`scripts/release_android.sh`](../../frontend/mobile/scripts/release_android.sh).

### Versioning rule

`pubspec.yaml` holds `version: <versionName>+<versionCode>`. Every build handed to anyone outside the
developer's machine **must** increase the number after `+`; Play and testers' devices refuse a
version code that is not higher than the installed one. The name follows semantic versioning:
1.1.0 is a feature release (the Focus Flow redesign) on top of the 1.0.0 baseline.

Per-ABI APKs carry version codes 1002 / 2002 / 4002 (Flutter adds `1000 × ABI index`) so that
they can coexist with the universal build; the AAB and universal APK carry 2.

## 2. Release build configuration

Configured in [`android/app/build.gradle.kts`](../../frontend/mobile/android/app/build.gradle.kts):

- **`signingConfigs.release`** reads the keystore path, alias and passwords from
  `android/key.properties`, or from `FITFLOW_KEYSTORE_PATH`, `FITFLOW_KEYSTORE_PASSWORD`,
  `FITFLOW_KEY_ALIAS` and `FITFLOW_KEY_PASSWORD` when the file is absent (CI). No secret is in the
  repository.
- **No silent fallback to the debug key.** The Flutter template signs release builds with the debug
  key; that line was removed. A task-graph check fails any `assembleRelease`/`bundleRelease` with a
  clear message when no upload key is configured, while debug builds still work on machines
  without the key.
- **`isMinifyEnabled = true`, `isShrinkResources = true`** with
  `proguard-android-optimize.txt` plus [`proguard-rules.pro`](../../frontend/mobile/android/app/proguard-rules.pro),
  which keeps line numbers for readable crash reports.
- **Dart obfuscation**: `--obfuscate --split-debug-info=build/debug-info`. The symbol files are
  kept (not shipped) so obfuscated Dart stack traces can be decoded with `flutter symbolize`.
- **Manifest**: Android 11+ `<queries>` declared for `https` and `mailto` so the privacy-policy and
  support links open on current devices.

## 3. Keystore management

### 3.1 Two keys, two owners

FitFlow uses **Play App Signing**:

| Key | Held by | Purpose | If lost |
|---|---|---|---|
| **App signing key** | Google (generated at first upload) | Signs what users actually install | Cannot be lost by the team |
| **Upload key** (`fitflow-upload.jks`) | Release owner | Proves an upload came from the team | Request an upload-key reset in Play Console; Google re-registers a new upload certificate |

This is why the upload key can be rotated but the app signing key never leaves Google — losing
the key that signs installed apps would mean users could never receive an update.

### 3.2 How the upload key was created

```bash
mkdir -p ~/.fitflow-signing && chmod 700 ~/.fitflow-signing
keytool -genkeypair -v -storetype PKCS12 \
  -keystore ~/.fitflow-signing/fitflow-upload.jks -alias fitflow-upload \
  -keyalg RSA -keysize 4096 -validity 10950 \
  -dname "CN=FitFlow Upload Key, OU=IT3060 WE 1.1, O=FitFlow, L=Malabe, ST=Western, C=LK"
chmod 600 ~/.fitflow-signing/fitflow-upload.jks
```

- 10 950 days (30 years) satisfies Play's requirement that keys remain valid beyond
  22 October 2033.
- The password was generated randomly (`openssl rand`), not chosen by a person.
- `keytool` is the one bundled with Android Studio
  (`/Applications/Android Studio.app/Contents/jbr/Contents/Home/bin/keytool`).

Certificate fingerprint (safe to share; needed for Firebase and API-key restrictions):

```
SHA-256: 93:B8:CF:64:31:72:92:77:8C:DA:A9:3D:ED:CB:96:90:67:EB:08:FA:3C:78:4D:4E:93:5D:29:8B:38:BA:57:51
SHA-1:   A9:69:9A:DD:60:F8:33:C0:3F:E3:6B:D0:7D:57:83:E2:08:2C:75:9F
```

### 3.3 Where the secrets live

| Secret | Location | In git? |
|---|---|---|
| Keystore file | `~/.fitflow-signing/fitflow-upload.jks` (outside the repository, mode 600) | No — and `*.jks`, `*.keystore` are ignored anyway |
| Passwords and alias | `~/.fitflow-signing/key.properties` (mode 600); `frontend/mobile/android/key.properties` is only a symlink to it | No — ignored by `android/.gitignore` |
| CI copies | GitHub Actions secrets: keystore as base64, passwords as separate secrets | No |

**Cloud-synced folders.** The project lives on a macOS Desktop that iCloud Drive syncs. Two
consequences were found and handled during this build:

1. A real `key.properties` inside the project would have been uploaded to iCloud with its
   passwords. It was moved to `~/.fitflow-signing/` (not synced) and replaced with a symlink.
2. iCloud created duplicate "`… 2`" copies of files while Gradle was writing them, which broke the
   Android build (`Type GeneratedPluginRegistrant is defined multiple times`), and its File Provider
   tagged files so that `codesign` rejected the iOS Flutter framework ("resource fork, Finder
   information, or similar detritus not allowed"). Renaming folders to `*.nosync` fixed the first
   problem but not the second, so build output now lives outside the synced Desktop entirely, in
   `~/Library/Caches/fitflow/mobile/`, reached through git-ignored symlinks with the normal names
   (`build`, `.dart_tool`, `android/.gradle`).

Recommendation for the team: keep working copies outside cloud-synced folders (for example
`~/dev/fitflow-redesign`).

`key.properties` format (values shown as placeholders):

```properties
storeFile=/Users/<you>/.fitflow-signing/fitflow-upload.jks
storePassword=<from password manager>
keyAlias=fitflow-upload
keyPassword=<from password manager>
```

Check before every commit: `git check-ignore -v frontend/mobile/android/key.properties` must print
the ignore rule, and `git status` must not list any `.jks` file.

### 3.4 Backup and access

1. **Two offline copies** of `fitflow-upload.jks`: an encrypted USB drive kept by the release owner
   and an encrypted archive in the team's shared password manager.
2. **Password** stored only in the password manager entry "FitFlow upload key", never in chat,
   email, screenshots or the report.
3. **Access**: the release owner and one named deputy. Other developers build debug variants and
   never need the key.
4. **Restore test**: once per semester, restore the backup on a clean machine and run
   `scripts/release_android.sh --verify`; the SHA-256 fingerprint must match §3.2.

### 3.5 Incidents

| Event | Action |
|---|---|
| Keystore lost, password forgotten | Play Console → App integrity → *Request upload key reset*; generate a new key with §3.2; update `key.properties` / CI secrets |
| Keystore or password exposed (e.g. committed) | Treat as compromised: request upload-key reset, rotate CI secrets, purge from git history, record in the incident log |
| Team member leaves | Rotate the password manager entry; if they held the file, request an upload-key reset |

### 3.6 CI signing (for when a release job is added)

```bash
# one-off, on the release owner's machine
base64 -i ~/.fitflow-signing/fitflow-upload.jks | pbcopy   # paste into secret FITFLOW_KEYSTORE_B64
```

The job decodes the secret to a temporary file, exports `FITFLOW_KEYSTORE_PATH` and the password
secrets, runs `scripts/release_android.sh`, and deletes the file in an `always()` step.

## 4. Build commands

From `frontend/mobile`:

```bash
# One command: clean, analyse, test, build AAB + APKs, verify, write evidence
scripts/release_android.sh

# Verify existing artefacts only
scripts/release_android.sh --verify
```

The equivalent individual commands:

```bash
flutter clean && flutter pub get
flutter analyze && flutter test
flutter build appbundle --release --obfuscate --split-debug-info=build/debug-info
flutter build apk --release --obfuscate --split-debug-info=build/debug-info
flutter build apk --release --split-per-abi --obfuscate --split-debug-info=build/debug-info
```

Outputs:

```
build/app/outputs/bundle/release/app-release.aab        → Google Play upload
build/app/outputs/flutter-apk/app-release.apk           → universal APK for direct installs
build/app/outputs/flutter-apk/app-<abi>-release.apk     → per-ABI APKs
build/app/outputs/mapping/release/mapping.txt           → R8 mapping (upload to Play / Crashlytics)
build/debug-info/*.symbols                              → Dart symbols (keep, do not ship)
```

## 5. Verification results

### 5.1 Integrity

| Check | Tool | Result |
|---|---|---|
| AAB signature | `jarsigner -verify` | **jar verified**, signer CN=FitFlow Upload Key |
| APK signature | `apksigner verify --print-certs` | **Verifies**, APK Signature Scheme v2, RSA 4096 |
| Signer matches keystore | SHA-256 of signer vs `keytool -list` | **Match** (`93b8cf64…5751`) |
| Not debug-signed | Signer DN | **Not** `CN=Android Debug` |
| Checksums recorded | `shasum -a 256` | In evidence log |

v1 (JAR) signing is absent on the APK by design: it is only needed below API 24, and minSdk is 24.

### 5.2 Size optimisation

| Artefact | Size | Note |
|---|---|---|
| `app-release.aab` | 48.5 MB | Upload file. ~60 % is `BUNDLE-METADATA` (native debug symbols + R8 map) that Play keeps for crash symbolication and never sends to devices |
| `app-release.apk` (universal) | 49.4 MB | All three ABIs; for testers only |
| `app-arm64-v8a-release.apk` | 17.5 MB | Native libraries stored uncompressed for faster start-up |
| **Play download, arm64 phone** | **≈ 8.0 MB** | `bundletool get-size total`, all API ranges |
| Play download, armeabi-v7a phone | ≈ 7.4 MB | |

R8 produced a 66 877-line mapping file, confirming Java/Kotlin code was shrunk and obfuscated.
Delivering the AAB rather than the universal APK cuts what a user downloads by about **84 %**.

### 5.3 Compatibility

| Check | Result |
|---|---|
| Min SDK 24 | Android 7.0 and later |
| Target SDK 36 | Meets Google Play's current target-API requirement for new apps and updates |
| ABIs | arm64-v8a (modern phones), armeabi-v7a (older 32-bit phones), x86_64 (Chromebooks, emulators) |
| Permissions requested | **None** that a user is asked for — no `INTERNET`, no `CAMERA`, no storage. Photos come through the system camera/picker. The only entry is Android's internal `DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION` |
| Install test | Installed from the AAB with `bundletool install-apks` on a Pixel 9a emulator (Android 16, API 36); onboarding, plan, logger, nutrition camera flow and settings exercised |

### 5.4 Start-up time (NFR3) — not yet verifiable

Cold start of the release build on the emulator measured 3.8–7.5 s (`am start -W`, six runs).
As a control, Android's own Settings app measured 2.5–5.5 s on the same emulator, so the emulator —
not the app — dominates. The NFR3 target (home screen within 2 s on a mid-range device) is therefore
**deferred to a physical-device measurement in Activity 6** rather than claimed here.
